# A failed Notification never fails the action that caused it

Every Notification is triggered inline, from the route action, immediately after the write that caused it — `better-sqlite3` transactions take a synchronous callback (`app/db/index.ts`), so a Knock call physically cannot go inside one, and Cadence has no job runner, queue or after-response hook to defer it to. The trigger functions in the Knock server module therefore catch everything and return without throwing: a Knock outage must not undo, or appear to undo, an action that has already committed. This deliberately diverges from the Acknowledgement emails two lines away at `app/routes/courses.$slug.refund.ts:75` and `app/routes/admin.refunds.tsx:130`, where `await sendEmail(...)` is left uncaught on purpose — an Acknowledgement is something the recipient is owed, a Notification is best-effort.

## Consequences

- **A dropped Notification is silent**, visible only as a `console.error` and in Knock's dashboard. We accept this over the alternative, which is telling a Student their refund request failed when the row is committed, or — because the comment action converts any thrown `Error` into a form error (`app/routes/courses.$slug.lessons.$lessonId.tsx:934`) — rendering "fetch failed" underneath a comment that saved perfectly.
- **The notification fires before the Acknowledgement email**, not after. Mailer-first would let a throwing `sendEmail` skip the Notification entirely; notification-first cannot skip the mailer, because the trigger cannot throw.
- **A crash between the committed write and the trigger loses that Notification permanently and invisibly.** Nothing records that it was owed. This closes the durability question [ADR 0014](./0014-knock-is-the-system-of-record-for-notifications.md) left open by noting an outbox "would not contradict" it: an outbox table plus a worker to drain it is larger than the whole of Notifications v1, so the PRD carries this as a named limitation instead.
- **Trigger functions own their recipient lookups** and return early on an empty recipient list, so the six call sites cannot get "who gets this" wrong and an empty `recipients` array never reaches Knock.
- **Preference writes are the exception.** `setEmailPreference` lives in the same module but still throws: the user flipped a switch and must be told when it did not take.
- **New Lesson Announced inverts the order**: it triggers first and sets the one-way `announced_at` only on reported success, so a swallowed failure cannot permanently burn the single announcement a lesson gets. It is the one trigger returning a boolean rather than `void`.
